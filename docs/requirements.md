# 食亨厨房知识助手 Demo｜需求分析

定位：产品经理管培生研究中的未售概念验证，不代表食亨现售功能。演示数据全部虚构；不接入真实餐厅配方。

## 角色与任务

- 主厨（上传页，只有一部手机）：用菜谱照片和口述快速留下经验；检查 OCR／转写草稿的原意，批准当前版，免得分店员工拿错步骤。
- 分店员工（问答页，主手机）：营业中忘记下一步或判断线索，针对约三道菜问短问题；看到有出处的当前版答案或一键求助主厨。只有发生求助时，右下角的小主厨手机才显示收到的消息。
- 购买者／管理者：要减少“老板/主厨被电话打断”与新店味道偏移风险；同时需要知道哪些问题不能靠问答替代带教、供货和现场判断。

## 核心问题与假设

1. 图／音输入能否比只打字更快生成可审草稿？本 Demo 只演示流程，未测 OCR、ASR 准确率。
2. 主厨批准版图文卡本身是否已能帮忙？不能把所有改善归因给 RAG。
3. 同问句、同模型下，本店资料与检索分别增加什么？评测拆成 A0「无本店资料」、A1「批准卡全文入模」和 A2「检索片段入模」；A0→A2 是本店知识＋检索的合并变化，不能宣称是 RAG 单独净收益。B2 搜索片段与 B3 RAG 的现场恢复时间要另测。
4. 资料已明确写明的成分要忠实回答；查不到、版本不明、禁忌/过敏原/食品安全缺少批准事实时，员工能否迅速问到主厨？小手机仅模拟通知，不是真实推送。

## 范围与非目标

范围：三道虚构菜、样例图片/音频、主厨上传与批准、员工问答、评测对照、引用来源、求助通知模拟。文字资料图可载入预置 OCR 草稿；备菜/炒菜/成品参照图只供人工对照，不会从菜品图反推配方。文本经人审后入库；准确称为「图文语音采集交互＋文本 RAG」。重点用番茄炒蛋的一组备菜与炒制状态图演示采集，其余两菜保留简短知识卡，避免堆三套图集。

非目标：自动判断味道、从成品照片推配方、直接以原图/原音做多模态检索、真实餐厅身份/租户系统、支付/门店业务接入、真实主厨消息推送、自动语音播报。录音和图片默认只在本机页面处理；不上传给 Qwen。

## 免费 Qwen 的判断

阿里云百炼北京地域的新用户免费额度有期限和条件，`qwen-turbo` 目前有 90 天的 100 万 token 免费额度；不是永久、任何账户都免费的 API。密钥必须留服务端。默认演示模式用明确标记的模拟生成器，使无密钥也可完整走流程；只有设置服务端密钥与显式开关后才尝试真实 Qwen。不能把真实秘方送给第三方，此 Demo 仅可发送虚构样本。上线真实试点另核合同用途、模型训练、留存删除和权限。
